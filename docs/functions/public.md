# Sign-in, account and set-up — Functions (libraries, API routes)

The API routes behind the public pages and the account page: sign-in and sign-out, password reset, two-step verification, sessions, email change, invitations, the first-run
set-up and public verification. The libraries they use are mostly in `src/lib/auth/` ([`shared.md`](./shared.md)).

## API routes: Sign-in and account security (`/api/v1/auth/`)

"Anyone (public)" routes run before a session exists and check CSRF and rate limits themselves, "Signed in" routes use `withAuth` with no `roles` and act on the caller's own account only, and every "window" below is the 5-minute window of `lib/auth/rate-limit.ts` (a slot is reserved first and handed back on success).

| Method | Route | File | Who | Description |
| --- | --- | --- | --- | --- |
| POST | `/api/v1/auth/change-password` | `auth/change-password/route.ts` | Signed in (own account) | `{ currentPassword, newPassword }`. The current password is re-verified (5 failures per account per window, refunded on success); the new one must pass `checkNewPasswordOnServer` and differ from the old (`INVALID_CURRENT_PASSWORD`, `VALIDATION`, `SAME_PASSWORD`, all 400). Success deletes the caller's other sessions and pending sign-in challenges, audits `PASSWORD_CHANGED` and emails a notice after the response. |
| POST | `/api/v1/auth/email-change/confirm` | `auth/email-change/confirm/route.ts` | Anyone (public) | Step 2 of an email change: `{ token }` from the link mailed to the NEW address. CSRF-checked, 10 failures per IP per window. Unknown, used, expired and "address taken meanwhile" links are the same 400 `INVALID_TOKEN`. Success switches `User.email`, deletes every session, reset link and challenge of the person, audits `EMAIL_CHANGED`, tells the OLD address, clears the session cookie and signs no one in. |
| POST | `/api/v1/auth/email-change/request` | `auth/email-change/request/route.ts` | Signed in (own account) | Step 1 of an email change: `{ newEmail, password }`. Re-verifies the password (5 wrong per window; `INVALID_PASSWORD`), refuses the current address (`SAME_EMAIL`), then always answers `{ requested: true }`: the lookup, the token and the mails run after the response, and a taken address gets a notice instead of a link, so nothing reveals who has an account. Limited to 3 verified requests per account and 3 per target address per window. |
| POST | `/api/v1/auth/forgot-password` | `auth/forgot-password/route.ts` | Anyone (public) | `{ email }`. Always answers 200 `{ requested: true }` (also for a malformed address or when the per-address limit of 3 per window is hit); the lookup, `createResetToken` and the email happen after the response. 10 requests per IP per window (429); every request counts, none is refunded. CSRF-checked. |
| POST | `/api/v1/auth/login/mfa` | `auth/login/mfa/route.ts` | Anyone (public; needs the `challenge` from sign-in step 1) | Sign-in step 2: `{ challenge, code }` or `{ challenge, recoveryCode }`. In order: CSRF, 503 `MFA_UNAVAILABLE` without `MFA_ENCRYPTION_KEY`, 30 per IP, a mis-shaped code (400 `VALIDATION`, slot refunded), the challenge (5 attempts, spent before the code is checked; 401 `INVALID_CHALLENGE`), 10 failures per account across challenges, then the factor (401 `INVALID_CODE`). A correct factor consumes the challenge and calls `completeSignIn`; a spent recovery code is audited (`MFA_RECOVERY_CODE_USED`), mailed, and the reply carries `recoveryCodesRemaining`. |
| POST | `/api/v1/auth/login` | `auth/login/route.ts` | Anyone (public) | Sign-in step 1: `{ email, password, remember }`. CSRF, then 30 attempts per IP and 5 per IP plus email (both hard, refunded on success) and a soft 10 per email reported as `accountThrottled`. Unknown account, no password and wrong password all give the same 401 `INVALID_CREDENTIALS` after one bcrypt compare. An account with an active second factor gets `{ mfaRequired, challenge }` and no session; otherwise `completeSignIn` sets the cookie. |
| POST | `/api/v1/auth/logout` | `auth/logout/route.ts` | Anyone (public) | Deletes the `Session` row matching the cookie and clears the cookie with its original attributes. Answers 200 even with no cookie or an unknown session, so a stale tab can always reach a clean state. CSRF-checked. |
| GET | `/api/v1/auth/me` | `auth/me/route.ts` | Signed in | `{ user, memberships }`: the session's user and the caller's active memberships (branch id and name, role). |
| POST | `/api/v1/auth/mfa/confirm` | `auth/mfa/confirm/route.ts` | Signed in (own account) | Step 2 of turning two-step verification on: `{ code }` (6 digits). 503 without a key, 5 wrong codes per account per window, 409 `NOT_ENROLLING` when no enrolment is open, 400 `INVALID_CODE`. Success activates the credential, returns the ten recovery codes once, deletes the caller's other sessions, audits `MFA_ENABLED` and mails a notice. |
| POST | `/api/v1/auth/mfa/disable` | `auth/mfa/disable/route.ts` | Signed in (own account) | Turns two-step verification off. Needs the password (checked first, so a wrong password never burns a code) AND a current `code` or `recoveryCode`; 5 failures per account per window; 409 `NOT_ENABLED`. Deletes the credential, recovery codes and challenges and the other sessions, audits `MFA_DISABLED`, mails a notice. |
| POST | `/api/v1/auth/mfa/enroll` | `auth/mfa/enroll/route.ts` | Signed in (own account) | Step 1 of turning two-step verification on: re-verifies `{ password }` (5 wrong per window), stores a fresh encrypted UNCONFIRMED secret and returns `{ secret, otpauthUrl }` (not cached) for the page to draw as a QR code in the browser. 409 `ALREADY_ENABLED` when a confirmed credential exists; 503 without `MFA_ENCRYPTION_KEY`. |
| POST | `/api/v1/auth/mfa/recovery-codes` | `auth/mfa/recovery-codes/route.ts` | Signed in (own account) | Replaces ALL recovery codes (used or not) with ten new ones, returned once. Needs `{ code }` from the authenticator, not a recovery code; 5 wrong per account per window; 409 `NOT_ENABLED`. Audits `MFA_RECOVERY_CODES_REPLACED` and mails a notice. |
| POST | `/api/v1/auth/reset-password` | `auth/reset-password/route.ts` | Anyone (public) | Step 2 of a password reset: `{ token, password }`. CSRF, 10 failures per IP per window. A weak or breached password is refused (400 `VALIDATION`) BEFORE the link is spent; unknown, used and expired links share one 400 `INVALID_TOKEN`. Success sets the hash, deletes every session and pending sign-in challenge, audits `PASSWORD_RESET`, mails a notice, clears the cookie; it signs no one in and leaves two-step verification on. |
| POST | `/api/v1/auth/sessions/revoke-others` | `auth/sessions/revoke-others/route.ts` | Signed in (own account) | Ends all the caller's sessions except the current one and returns `{ revoked: n }`; no password needed because it only reduces access. 10 per account per window; audits `SESSIONS_REVOKED` when `n` is above 0. |
| POST | `/api/v1/auth/sessions/revoke` | `auth/sessions/revoke/route.ts` | Signed in (own account) | Ends one of the caller's own other sessions: `{ sessionId }`. The current session is refused (400 `CURRENT_SESSION`); an unknown, expired or someone else's id are the same 404. 30 per account per window; audits `SESSION_REVOKED` with the device label. |
| GET | `/api/v1/auth/sessions` | `auth/sessions/route.ts` | Signed in (own account) | The caller's unexpired sessions as `{ sessions }` (id, device label, `current`, `createdAt`, `lastUsedAt`, `keptSignedIn`), current first. Never a token or an address. |

## API routes: Account (`/api/v1/account/`)

| Method | Route | File | Who | Description |
| --- | --- | --- | --- | --- |
| PATCH | `/api/v1/account/profile` | `account/profile/route.ts` | Signed in (own account) | Edits the caller's display name: `{ name }`, normalised and checked by `checkName` (at most 100 characters, no control or bidirectional-override characters; 400 `VALIDATION` otherwise). 10 changes per account per window, every attempt counted. Audits `PROFILE_UPDATED` (before and after) only when the stored name actually changed; returns `{ user }`. |

## `src/lib/invitations/`

Invitations to join a branch, from the administrator's side (create, resend, revoke, list) and the invitee's side (preview, accept), where every write is audited in the same transaction as the change and no audit row carries a token, hash or password.

| File | Description |
| --- | --- |
| `service.ts` | `createInvitation`, `resendInvitation`, `revokeInvitation`, `listOpenInvitations`, `previewInvitation`, `acceptInvitation`, `PublicInvitation`. Create takes a Postgres advisory lock on the address, refuses an active or deactivated member (`ALREADY_MEMBER`, `DEACTIVATED_MEMBER`), a branch outside the caller's `AdminScope` (`OUT_OF_SCOPE`) and an `ADMIN` invitation from anyone but a superadmin (`ADMIN_ONLY`), and revokes the earlier open invitation to that address and branch. Accept is one transaction with a conditional update: a new address gets a `User` (`emailVerified` set) and a `Membership`; an existing account is attached only when its owner is the signed-in viewer (`SIGN_IN_REQUIRED`, `WRONG_ACCOUNT`, `ALREADY_MEMBER`, `INVALID`, `INPUT_REQUIRED`). |
| `status.ts` | Client-safe `invitationStatus` and `isLiveInvitation`: an invitation's state (`accepted`, `revoked`, `expired`, `pending`) derived from its three timestamps, never stored. The API and the Users page use the same function, so what an administrator sees matches what accept enforces. |
| `token.ts` | `newInvitationToken` (32 random bytes as base64url, always 43 characters), `hashInvitationToken` (SHA-256 hex), `isInvitationToken` (cheap shape check) and `INVITATION_TTL_DAYS` (7). The token travels in the URL fragment, never in a server log. |

## API routes: Invitations (`/api/v1/invitations/`)

`accept` and `preview` are public (the link's 43-character token, valid 7 days and stored only as a SHA-256 hash, is the credential); the rest are for administrators, where a branch administrator is limited by `scopeOrForbidden` to their own branches and never sees or touches an `ADMIN`-role invitation, and a superadmin is not limited.

| Method | Route | File | Who | Description |
| --- | --- | --- | --- | --- |
| POST | `/api/v1/invitations/[id]/resend` | `invitations/[id]/resend/route.ts` | Administrators, own branches only | Issues a fresh link and a fresh seven days for an OPEN invitation (pending or expired); the earlier link stops working at once. 3 resends per invitation per window; the email goes out after the response, limited to 5 per address. Unknown, accepted, revoked and out-of-scope ids are one 404 `NOT_FOUND`. Audited as `INVITATION_RESENT` in the same transaction. |
| DELETE | `/api/v1/invitations/[id]` | `invitations/[id]/route.ts` | Administrators, own branches only | Revokes an open invitation (sets `revokedAt`, audits `INVITATION_REVOKED`) and returns `{ revoked: true }`. An accepted, already revoked, unknown or out-of-scope id is the same 404. |
| POST | `/api/v1/invitations/accept` | `invitations/accept/route.ts` | Anyone (public; a signed-in session is read if present) | `{ token, name?, password? }`. CSRF, 10 failures per IP per window (a success, a typo in the name or password, and the sign-in-first, wrong-account and already-member answers are refunded). No account for the address: creates it from `name` and `password` (checked by `checkName` and `checkNewPasswordOnServer` before the link is spent) plus the membership, and does NOT sign the person in. An existing account is attached only to its signed-in owner: otherwise 409 `SIGN_IN_REQUIRED` or 403 `WRONG_ACCOUNT`; 409 `ALREADY_MEMBER`. Unknown, malformed, used, revoked, expired and deactivated-person links are one 400 `INVALID_TOKEN`. |
| POST | `/api/v1/invitations/preview` | `invitations/preview/route.ts` | Anyone (public; a signed-in session is read if present) | `{ token }`: what the accept page shows before anyone commits: school name, branch, role and its label, the MASKED address, `accountExists`, and `viewer` (`none`, `invitee` or `other`). CSRF, 40 per IP per window; a token that is not the 43-character form, or is unknown, used, revoked or expired, is one 400 `INVALID_TOKEN`. |
| GET, POST | `/api/v1/invitations` | `invitations/route.ts` | Administrators, own branches only | GET lists the open invitations (pending, and expired ones that can be resent), newest first, with offset pagination; never a token or hash. POST `{ email, role, branchId }` (strict body) creates one and returns 201 with the invitation: 30 per administrator and 3 per address per window; 409 `ALREADY_MEMBER` or `DEACTIVATED_MEMBER`; 400 for an unknown branch; 403 for a branch outside the caller's scope, or an `ADMIN` invitation unless the caller is a superadmin; an earlier open invitation to the same address and branch is revoked. The mail is sent after the response (5 per address per window; beyond that the invitation exists but the mail is withheld). |

## `src/lib/setup/`

| File | Description |
| --- | --- |
| `status.ts` | `isSetupComplete()`: reads `SystemSettings` (`id` `global`) and returns true or false, or `null` (unknown) when the database read fails, instead of throwing. Callers treat `null` as "do not redirect": `/` and `/login` redirect to `/setup` only on `false`, `/setup` redirects to `/login` only on `true`. |

## API routes: First-run setup (`/api/v1/setup/`)

| Method | Route | File | Who | Description |
| --- | --- | --- | --- | --- |
| GET, POST | `/api/v1/setup` | `setup/route.ts` | Anyone (public) | GET returns `{ setupComplete, requiresToken }` and answers `setupComplete: false` if the database read fails (fail open, so a deployer is not locked out). POST is the one-time bootstrap `{ name, email, password, setupToken? }`: CSRF, 5 attempts per IP per window (refunded on success), the new-password rule, the breach check, and `SETUP_TOKEN` when the server has one (header `x-setup-token` or body, timing-safe compare; 401 `BAD_SETUP_TOKEN`). One transaction flips `SystemSettings.setupComplete` with a conditional update, upserts the four fixed branches, creates the first user as a superadmin with an `ADMIN` membership in the first branch and writes `SETUP_WIZARD_COMPLETE`. 201 on success, 409 `ALREADY_COMPLETE` afterwards, 409 `DUPLICATE_EMAIL`; it signs no one in. |

## API routes: Result verification (`/api/v1/verify/`)

| Method | Route | File | Who | Description |
| --- | --- | --- | --- | --- |
| GET | `/api/v1/verify/[token]` | `verify/[token]/route.ts` | Anyone (public) | Checks a printed verification code. 60 lookups per client address per window (429 `RATE_LIMITED`). Returns `{ verification }` from `verifyToken` (a `genuine` flag, school, branch, class, term and publish date, plus pupil name, subject, mark and grade as the branch's verification-page settings allow: by default the pupil as first name and last initial and the subject are shown, mark and grade are hidden) or 404 `NOT_FOUND`, the same answer for an unknown, never-issued and withdrawn code. |
