# Shared — Functions (libraries used across the app)

What every other part leans on: the authentication library and the `withAuth` / `withAuthGated` route guards (`src/lib/auth/`), the API helpers (response envelope, ids,
validation, pagination), email, the Content-Security-Policy, the database client, the request proxy and the start-up checks.

## `src/lib/auth/`

Sessions, passwords, the route and page guards, branch authority, CSRF, rate limiting and the account-security helpers (reset links, email change, active devices); server code, except the rows marked "client-safe", which have no Node imports and are also used by browser code.

| File | Description |
| --- | --- |
| `audit.ts` | `auditPersonEvent(userId, action, { before, after, reason })`: writes one `AuditLog` row (`targetType` `User`, actor and target both the person) for a person-level security event. The auth routes pass `PASSWORD_CHANGED`, `PASSWORD_RESET`, `MFA_ENABLED`, `MFA_DISABLED`, `MFA_RECOVERY_CODES_REPLACED`, `MFA_RECOVERY_CODE_USED`, `EMAIL_CHANGE_REQUESTED`, `EMAIL_CHANGED`, `SESSION_REVOKED`, `SESSIONS_REVOKED` and `PROFILE_UPDATED`; the action string is not validated here. |
| `branch-access.ts` | `isSuperAdmin`, `adminScope`, `canAdminister`, `mayAdminister`, `resolveBranchRole`, `branchIdsFor`, `heldRoleIn`, `EVERY_BRANCH`: the one place that turns a person's ACTIVE memberships (`deactivatedAt` null) plus `User.isSuperAdmin` into authority. A superadmin counts only while holding at least one active membership; an `ADMIN` membership administers only its own branch; `resolveBranchRole` and `branchIdsFor` count only staff roles (`ADMIN`, `TEACHING_STAFF`, `NON_TEACHING_STAFF`), while `heldRoleIn` also counts `STUDENT` and `PARENT`. No membership means `null`, never a default role. |
| `branch-gate.ts` | `withAuthGated(level, handler, { roles })` and `GateLevel`: `withAuth` plus a check that every branch the request names belongs to the caller. Levels: `administer`, `staff-write`, `staff-read`, `read-any` (any membership, including student and parent). The branches a request names are every `branchId=` in the URL and the `branchId` of its JSON body; the body is read for every method but `GET` and `HEAD`, whatever its `Content-Type`, up to `MAX_BODY_BYTES` (1 MiB, through `readBoundedText` on a copy of the request, so the handler can still read its own; larger is a 413 `PAYLOAD_TOO_LARGE`). Two different ids, or a body `branchId` that is not text, are a 400 `VALIDATION`. A foreign branch is 404 when it came from the URL and 403 `FORBIDDEN` when it came from a body; a request naming no branch reaches the handler, which must answer its own 400. |
| `complete-sign-in.ts` | `completeSignIn(req, user, remember, extra)`: the only place a session is created from a sign-in (`/auth/login` without a second factor, and `/auth/login/mfa`). Deletes the session whose cookie the browser presented, uses the shorter administrator lifetime for anyone with an active `ADMIN` membership or a superadmin, calls `createSession`, and returns `ok({ user, ...extra })` with the cookie set (persistent only when `remember`). |
| `csrf.ts` | `validateCSRF(req)`: the same-origin check for state-changing requests (no CSRF tokens). Refuses `Sec-Fetch-Site` of `cross-site` or `same-site`; then `Origin` (or `Referer`) must equal the request's `Host`, and a request with neither is refused. `X-Forwarded-Host` is read only when `TRUST_FORWARDED_HOST=true`. `withAuth` applies it to every method except GET, HEAD and OPTIONS; public routes call it themselves. |
| `email-change.ts` | `createEmailChangeToken(userId, newEmail)`, `confirmEmailChange(token)`, `EMAIL_CHANGE_LINK_MINUTES` (60): links for changing a sign-in address, stored as SHA-256 hashes in `EmailChangeToken`, one live request per person. Confirming is one transaction that claims the link with a conditional update, sets `User.email` and `emailVerified`, and deletes the person's sessions, reset links, `MfaChallenge` rows and other change requests. Returns null for an unknown, used or expired link, and when the new address was taken meanwhile (unique-index error rolls back). |
| `mask-email.ts` | `maskEmail(email)`: `amina@school.example` becomes `a***@school.example`; anything not shaped like an address becomes `***`. Used in the invitation preview and in security notices. |
| `memberships.ts` | `getUserMemberships(userId)` and `UserMembership`: the person's ACTIVE memberships (`deactivatedAt` null) as `{ branchId, branchName, role }`, oldest first. Feeds `requirePageSession` and `GET /api/v1/auth/me`. |
| `page-session.ts` | `requirePageSession`: the session guard for pages (the API's is `withAuth`), wrapped in React `cache`. No session redirects to `/login`; otherwise returns `{ session, memberships, isAdmin, isSuperAdmin, roleLabel }`. `isAdmin` means an `ADMIN` membership or a superadmin; `roleLabel` is the most senior held role, or "No role yet". Every page must call it itself: a layout does not re-render on client navigation, so it is display only. |
| `password-policy.ts` | Client-safe (no Node imports) password rules: `checkNewPassword`, `passwordByteLength`, `PASSWORD_MAX_LENGTH` (128), `PASSWORD_MAX_BYTES` (72). A NEW password needs 8 characters or more, at most 128 characters and 72 bytes (bcrypt silently ignores the rest, so longer is rejected rather than truncated), a letter and a digit. Sign-in deliberately does not apply the byte limit. |
| `password-reset.ts` | `createResetToken`, `isLiveResetToken`, `resetPasswordWithToken`, `RESET_TOKEN_TTL_MS`: single-use reset links in `PasswordResetToken` (SHA-256 hash only, one live link per person). Claiming is a conditional update inside one transaction that sets the new hash, deletes every session and `MfaChallenge` of the person (the second factor itself is untouched) and their other links; null for an unknown, used or expired token. |
| `password.ts` | `hashPassword`, `verifyPassword`, `BCRYPT_COST` (12), plus re-exports of the two size limits. `hashPassword` rejects (RangeError) a password over 72 bytes instead of truncating it. `verifyPassword` always runs a bcrypt compare, against a hash generated at module load when the user or hash is missing, so "no such user" costs the same as "wrong password". |
| `profile-policy.ts` | Client-safe `checkName(input)` and `NAME_MAX_LENGTH` (100): trims, NFC-normalises and collapses whitespace, counts characters by code point, and refuses control and bidirectional-override characters (zero-width joiners are allowed). Returns `{ ok, name }` or `{ ok: false, message }`; the name form and `PATCH /api/v1/account/profile` share it. |
| `pwned-password.ts` | `isBreachedPassword`, `checkNewPasswordOnServer`, `BREACHED_MESSAGE`: the Have I Been Pwned range check (only the first 5 hex characters of the SHA-1 leave the server, `Add-Padding` on, 2-second timeout). Fails open: any network error or odd answer counts as "not breached". `PWNED_PASSWORD_CHECK=off` disables it, `PWNED_PASSWORD_URL` changes the endpoint. `checkNewPasswordOnServer` is the shape rules then the breach check. |
| `rate-limit.ts` | `reserveAttempt`, `refundAttempt`, `checkRateLimit`, `getClientIp`, `DEFAULT_MAX_ATTEMPTS` (5), `MAX_TRACKED_IDENTIFIERS` (10,000): an in-memory limiter over a sliding 5-minute window, reserve first and refund on success. State lives in this one process; the oldest-touched keys are dropped past 10,000. The function bodies must stay free of `await` (that is what makes a reservation atomic). `getClientIp` trusts only `CLIENT_IP_HEADER` (default `x-real-ip`, or the Nth entry from the right of `x-forwarded-for` with `TRUSTED_PROXY_HOPS`) and otherwise uses one shared `unproxied` bucket. |
| `reset-constants.ts` | Client-safe `RESET_LINK_MINUTES` = 30, so the reset email, `ForgotPasswordForm` and `password-reset.ts` (`RESET_TOKEN_TTL_MS`) share one number. |
| `session-devices.ts` | The "Active devices" data: `listSessions(userId, currentSessionId)` (unexpired sessions, current first, then by last use; device label, created and last-used times, `keptSignedIn`; never a token or an address), `revokeOwnSession` (null for a missing session and for someone else's, so ids cannot be probed) and `revokeAllOtherSessions` (same delete as `revokeOtherSessions` in `session.ts`). |
| `session.ts` | Database sessions: `createSession`, `getSession`, `getSessionFromRequest`, `setSessionCookie`, `clearSessionCookie`, `deleteSessionByToken`, `revokeOtherSessions`, `revokeUserSessions`, `purgeExpiredSessions`. The token is 32 random bytes and only its SHA-256 is stored in `Session`. Idle expiry slides 30 days (written at most every 5 minutes); absolute caps are 12 hours when not remembered (the default) and 90 days when remembered, cut to 7 days for administrators (`completeSignIn` passes `admin`); at most 10 sessions per person (oldest created are evicted). Cookie `aleemaan.session-token`, or `__Host-aleemaan.session-token` when `APP_URL` is https; HttpOnly, SameSite=Lax. |
| `user-agent.ts` | `describeUserAgent(userAgent)`: a short label such as "Chrome on Windows" from the stored user agent (first 255 characters), "Unknown device" when nothing matches. Pattern order matters (Edge and Opera also say "Chrome"). Only ever rendered as text. |
| `with-auth.ts` | `withAuth(handler, { roles, superAdmin })` and `AuthContext`: the guard every authenticated API handler uses. Order: CSRF for every method but GET, HEAD and OPTIONS (403 `CSRF`), then the session cookie (401 `UNAUTHENTICATED`), then `roles` (an active membership with any listed role in ANY branch; a superadmin passes only when the list includes `ADMIN`) or `superAdmin: true`, else 403 `FORBIDDEN`. It then sanitises the route's path params, runs the handler and adds `Cache-Control: private, no-store` if none was set. Throws at module load for `permissions`, a `superAdmin` that is not `true`, or an empty `roles`. `roles` alone says nothing about which branch: use `withBranch` or `withAuthGated`. |
| `with-branch.ts` | `withBranch({ of, as, where, refuse }, handler)` and `branchGrant(userId, branchId, as)`: runs the handler only after the branch it acts on is resolved and the caller's authority there checked. `as` is `administer` (superadmin or `ADMIN` of that branch), `staff-read` or `staff-write` (`ADMIN` or `TEACHING_STAFF` there). An unknown or foreign branch is a 404; a branch named in a body and refused for `administer`, or a staff member lacking the role for `staff-write`, is a 403 `FORBIDDEN`. Composed inside `withAuth` and after `validate()` (ADR 0015). |

## `src/lib/auth/mfa/`

Two-step verification (authenticator codes, single-use recovery codes, the pending sign-in challenge and encrypted secrets), which is unavailable (503 from the routes, and no development fallback key) unless `MFA_ENCRYPTION_KEY` holds base64 of 32 bytes.

| File | Description |
| --- | --- |
| `base32.ts` | `base32Encode` (RFC 4648 alphabet, no `=` padding, what authenticator apps expect) and `base32Decode` (accepts lower case, spaces, hyphens and `=`; returns null on any other character). `base32Decode` is used only by tests. |
| `challenge.ts` | The pending state between a correct password and a correct second factor, in `MfaChallenge` (not a session, no cookie): `createChallenge(userId, remember)`, `spendChallengeAttempt`, `consumeChallenge`, `deleteUserChallenges`. 256-bit token held by the sign-in page, only its SHA-256 stored; lives 5 minutes (`CHALLENGE_TTL_MS`), 5 attempts (`CHALLENGE_MAX_ATTEMPTS`, spent by a conditional increment BEFORE the code is checked), at most 5 live per person. |
| `codes.ts` | Client-safe code rules (no `node:crypto`; the sign-in and account forms use them too): `normaliseTotpCode` (6 digits, spaces and hyphens ignored), `normaliseRecoveryCode` (10 characters of Crockford base32, case and hyphen ignored, O read as 0, I and L as 1) and `RECOVERY_CODE_ALPHABET`, `RECOVERY_CODE_LENGTH` (10), `RECOVERY_CODE_COUNT` (10). Null means a typo, not a wrong guess. |
| `factor.ts` | `parseSecondFactor({ code, recoveryCode })`: returns a `SecondFactor` only when exactly one of the two is present and shaped right, else null. Routes answer 400 and refund their rate-limit slot, so a typo never counts against the person. |
| `recovery-codes.ts` | `generateRecoveryCode`, `generateRecoveryCodes`, `hashRecoveryCode`: codes look like `XXXXX-XXXXX` (50 random bits, shown once) and are stored as HMAC-SHA256 under a key derived from `MFA_ENCRYPTION_KEY`, so a stolen table alone cannot be ground offline. Throws `MfaUnavailableError` without a key. |
| `secret-box.ts` | `encryptSecret`, `decryptSecret`, `deriveKey`, `mfaConfigured`, `MfaUnavailableError`, `MFA_KEY_ENV`: AES-256-GCM boxes `v1.<iv>.<ciphertext>.<tag>` with the user id as additional authenticated data, so a row copied to another person fails to decrypt. Purpose keys come from the root key by HKDF-SHA256. A wrong key, wrong owner or tampering throws `MfaUnavailableError` (routes answer 503; an operator runs `pnpm mfa:reset`). |
| `service.ts` | The data side of two-step verification: `hasActiveMfa`, `getMfaStatus`, `unusedRecoveryCodeCount`, `beginEnrolment`, `confirmEnrolment`, `verifyTotpForUser`, `spendRecoveryCode`, `verifySecondFactor`, `regenerateRecoveryCodes`, `disableMfa`. An unconfirmed credential is invisible to sign-in; `beginEnrolment` returns null if a confirmed one exists. Every use-once rule (confirm, TOTP step replay via `lastUsedStep`, recovery code) is a conditional update decided by its row count. |
| `totp.ts` | RFC 6238 over RFC 4226 written in place: 6 digits, 30-second step, HMAC-SHA1, 20-byte secret, accepts the current step and one either side. `verifyTotp` returns the matching step (refusing any step at or below `afterStep`, comparing every candidate in constant time); also `hotp`, `totpAt`, `stepAt`, `generateTotpSecret`, `otpauthUrl`. `totpAt` is used only by tests. |

## `src/lib/api/`

The shared contract of every JSON route: the response envelope, what a URL id may look like, list parameters and request validation.

| File | Description |
| --- | --- |
| `envelope.ts` | The response shape of every API route. `ok(data, meta = {}, status = 200)` gives `{ data, meta, error: null }`. `fail(message, status, code?, details?)` gives `{ data: null, meta: {}, error: { code, message, details? } }`; `code` defaults to the status as a string and `details` (`ErrorDetail[]` of `path` and `message`) is included only when non-empty. `noStore(response)` sets `Cache-Control: no-store` on the response it is given and returns it. |
| `ids.ts` | What an id from a URL may look like. `ID_PATTERN` (letters, digits, `_`, `-`, 1 to 64 characters) and `isPlausibleId` check an id before it reaches a query. `isUnusablePathValue` (a control character, an unpaired surrogate or over 256 characters) and `sanitizePathParams` replace such a path value with `"_"`, so the route answers as for an unknown id; `withAuth` applies it to the `params` of every route it wraps (the portal and `verify` routes do not use `withAuth`). `isMalformedPath` (broken percent-encoding) is what `src/proxy.ts` turns into a 400. |
| `pagination.ts` | Strict list parameters: a repeated value, or anything but 1 to 9 digits, is refused with the field named, never clamped. `parseOffsetPagination` (`?page=&limit=`; defaults 1 and 25, `limit` up to 100, `page` up to 100 000) and `parseCursorPagination` (`?limit=&after=`) return `{ ok: true, ... }` or `{ ok: false, issues }`; `offsetMeta` builds `{ page, limit, total, pages, hasNext }`. The cursor helpers (`encodeCursor`, `decodeCursor`, `cursorMeta`) are used by no route. Only the `members` and `invitations` routes call the offset parser; `students` and `finance/invoices` parse `page` and `limit` themselves. |
| `read-body.ts` | `readBoundedText(req, cap)`: the request body as text, read no further than `cap` bytes, or `null` when it is larger. A declared `content-length` over the cap is refused without reading anything; a body with no declared length (a chunked upload), or one longer than it said, is read until the cap is passed and then dropped, so a sender that never finishes cannot hold the request open. The cancel of the stream is not awaited: for one half of a tee it settles only when the other half is cancelled too. Used by `validate` and by `withAuthGated`. |
| `validate.ts` | `parseRequest(req, { body?, query? })` returns `{ ok: true, input }` or `{ ok: false, response }`; `validate(schemas, handler)` runs the handler only on valid input (its fourth argument) and goes inside `withAuth`. Refusals: query schema failure 400 `VALIDATION`; body over `MAX_BODY_BYTES` (1 MiB: a declared `content-length` over it is refused unread, otherwise the body is read through `readBoundedText` only until it passes the cap) 413 `PAYLOAD_TOO_LARGE`; body not JSON 400 `INVALID_BODY`; body schema failure 400 `VALIDATION`. `details` hold at most 20 entries, with paths prefixed `query.` or `body.`. Unknown keys are stripped or refused by the zod schema, never passed on. |

## `src/lib/email/`

Outgoing email: the plain-text body of each message and the transport that sends it.

| File | Description |
| --- | --- |
| `messages.ts` | Builders returning `{ to, subject, text }`: `resetEmail`, `passwordChangedEmail`, `mfaEnabledEmail`, `mfaDisabledEmail`, `recoveryCodeUsedEmail(to, remaining)`, `recoveryCodesReplacedEmail`, `emailChangeConfirmEmail`, `emailChangeRequestedNotice`, `emailChangedNotice`, `emailChangeTakenNotice`, `invitationEmail`, plus `resetLink` and `invitationLink`. Links start from `APP_URL` (default `http://localhost:3000`) and carry the token in the URL fragment, so it is not in server logs or a `Referer`. The new address in the change notices is masked with `maskEmail`. The invitation text is the same whether or not the address has an account. |
| `transport.ts` | `getEmailTransport()`, `sendEmailQuietly(message)` and `EmailMessage` (`to`, `subject`, `text`). `EMAIL_TRANSPORT` picks `resend` (needs `RESEND_API_KEY` and `EMAIL_FROM`), `console` (prints the whole message), `file` (JSON lines to `EMAIL_FILE`, for tests) or `inbox` (in-memory dev inbox; throws unless the dev tools are on). Unset: `resend` if `RESEND_API_KEY` is set, else `inbox` if the dev tools are on, else `console` (one warning in production). An unknown value throws. `sendEmailQuietly` never throws: it logs and returns `false`, so a send error cannot reveal whether an address has an account. |

## `src/lib/security/`

The page Content-Security-Policy, as pure functions.

| File | Description |
| --- | --- |
| `csp.ts` | `generateNonce()` (16 random bytes, base64), `buildCsp({ nonce, dev, https })` and `API_CSP`. The page policy allows `'self'` for default, font, connect, base and form targets; scripts need the request's nonce (`'strict-dynamic'`, plus `'unsafe-eval'` only in dev) and so do styles (no `'unsafe-inline'`); images also allow `data:` and `blob:`; no objects, no framing. `upgrade-insecure-requests` is added only when `https` (it would break a plain-HTTP LAN install) and `ws:` and `wss:` only in dev. `API_CSP` (`default-src 'none'; frame-ancestors 'none'`) is what `next.config.ts` puts on `/api/*`; `src/proxy.ts` calls the other two. |

## `src/lib/dev/`

The store behind the development email inbox.

| File | Description |
| --- | --- |
| `email-inbox.ts` | `recordDevEmail`, `getDevEmails`, `clearDevEmails`, the `DevEmail` type (`id`, `to`, `subject`, `text`, `sentAt`), `MAX_DEV_EMAILS` (50) and `MAX_DEV_EMAIL_TEXT` (20 000). The in-memory store the `inbox` email transport writes to: newest first, the oldest dropped past 50, a body over 20 000 characters cut with a "[truncated]" marker. ## API routes: Dev (`/api/v1/dev/`)

| Method | Route | File | Who | Description |
| --- | --- | --- | --- | --- |
| GET, DELETE | `/api/v1/dev/email-inbox` | `dev/email-inbox/route.ts` | Anyone (public) where the dev tools are open; staging needs the `x-dev-tools-token` header; 404 where they are off | The dev inbox's data. No `withAuth`; the gate is `devToolsAccess()`. `GET` returns `{ emails, mode }` (captured messages, newest first, and `appEnv()`); `DELETE` empties the store (`{ cleared: true }`) and, whenever the tools are on, needs a same-origin request (`validateCSRF`, else 403 `CSRF`). Off (always in production): 404 `NOT_FOUND`. Staging: a missing token is 401 `TOKEN_REQUIRED` at no cost; a wrong one is 401 and counts against 5 per IP per 5 minutes (then 429 `RATE_LIMITED`); a right one is refunded; tokens are compared as SHA-256 digests with `timingSafeEqual`. All answers are `no-store`. |

Small modules most of the app imports: the database client, brand strings, role names, theme cookie, development-tools gate and a relative-time formatter.

| File | Description |
| --- | --- |
| `brand.ts` | `brand`: AlEemaan's per-repo strings: `name`, `tagline`, `description`, the sign-in `login` headline, blurb and points, and `place` (the singular and plural word for a branch). One of only two brand files, with `src/app/brand.css`. Read by the root layout, manifest, `AppShell`, `AuthShell`, the offline page and the email messages. Nothing reads `place` today. |
| `db.ts` | `prisma`: the one `PrismaClient`, cached on `globalThis` outside production so hot reload does not open a new connection pool per edit. | `dev-tools.ts` | The one gate for development affordances (today the dev email inbox). `appEnv(env?)` returns `development`, `staging` or `production` from `VERCEL_ENV`, `APP_ENV` and `NODE_ENV`; an unrecognised `APP_ENV` counts as production. `devToolsAccess(env?)` returns `{ kind: "off" }` (production always; staging unless `DEV_TOOLS=true` and a non-empty `DEV_TOOLS_TOKEN`; development with `DEV_TOOLS=false`), `{ kind: "open" }` (development) or `{ kind: "token", token }` (staging, switched on). `devToolsEnabled(env?)` is `kind !== "off"`. | `roles.ts` | `ROLE_LABELS`: the display name of each Prisma `Role` (`ADMIN` Administrator, `TEACHING_STAFF` Teaching staff, `NON_TEACHING_STAFF` Non-teaching staff, `STUDENT` Student, `PARENT` Parent). | `theme.ts` | The light/dark choice: `THEME_COOKIE` (`theme`), the `Theme` type, `parseTheme` (anything but `"light"`, including a missing cookie, is `dark`) and `THEME_MAX_AGE_SECONDS` (one year). ## `src/` (top-level files)

Next.js loads `instrumentation.ts` and `proxy.ts` by name; `instrumentation-node.ts` is the secret check the startup hook calls.

| File | Description |
| --- | --- |
| `instrumentation-node.ts` | `checkRequiredSecrets(env?, exit?)`: collects the problems with required secrets (today only `portalSecretProblem`: the portal cookie secret `SESSION_SECRET`, at least 32 characters, not the retired default, not repetitive) and, if there are any, prints them without the secret and exits the process with code 1. It exits instead of throwing because a throw in `register()` leaves Next 16 running and answering every request with a 500. `env` and `exit` are parameters so tests can pass their own. |
| `instrumentation.ts` | Next's `register()` hook, run once when the server starts. On the Node runtime and not during `next build`, it calls `checkRequiredSecrets()` from `instrumentation-node.ts`, so a server missing a required secret refuses to start. The check lives in its own file so the edge bundle never sees `process.exit`. |
| `proxy.ts` | Next 16's `proxy` (the former middleware); runs on page requests and `/api/*`, not on `_next/static`, `_next/image`, `favicon.ico` or prefetches. Broken percent-encoding in the path is answered 400 (`isMalformedPath`) before any route runs. `/api/*` then passes through (its static CSP is in `next.config.ts`). Every other request gets a fresh nonce and the `buildCsp` policy, on the request headers (Next stamps its scripts from them) and on the response; `CSP_REPORT_ONLY=true` sends the report-only header, and `https` comes from `APP_URL`. No authentication, no redirects. |
