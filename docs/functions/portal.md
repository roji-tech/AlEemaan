# Parent and student portal — Functions (services, libraries, API routes)

The portal's own session (a signed, stateless cookie), sign-in, and the read and write routes behind `/portal`. None of it uses the school app's `withAuth` session.

## `src/lib/portal/`

The parent and student portal's own sign-in and data access, separate from staff accounts (no `User` row, no `Session` row).

| File | Description |
| --- | --- |
| `access-input.ts` | `portalAccessInput`, the zod schema the settings route takes (task 0040): both actors, every key, nothing else (strict), plus the rules of `portalAccessProblems` as issues. Server only: the Settings screen calls `portalAccessProblems` from `access.ts` directly, because importing zod into a client component makes the browser report a Content-Security-Policy violation (zod probes for `eval` when it loads). |
| `access-service.ts` | The database side of the portal access setting (task 0040), one `SettingValue` row per branch (scope BRANCH, key `portal_access`): `getPortalAccess(branchId)`, `getPortalAccessByBranch(ids)` (one query for a family spread over branches) and `setPortalAccess(branchId, value, actorUserId)`, which stores and writes a `SettingAudit` row (`CHANGED`, or `CHANGED_WIDENING` when somebody got more) in the same transaction, and writes nothing when nothing changed. |
| `access.ts` | What a pupil and a guardian may do in the portal (task 0040), pure: `ACTORS`, `CAPABILITIES` (overview, results, invoices, materials, submitWork, takeQuizzes, siblings), `PRACTICE_LEVELS`, `DEFAULT_PORTAL_ACCESS` (the maintainer's table: a pupil has no invoices and no siblings; a guardian has invoices and every linked child but never hands in work or takes a quiz), `resolvePortalAccess` (tolerant: a missing or damaged value is the default, key by key), `accessFor`, `allowedTabs`, `portalAccessProblems` (an actor must keep one section, and work or quizzes need the coursework section; plain code shared by the server and the screen) and `widens`. |
| `auth.ts` | The portal's stateless session: `signPortalSession` and `verifyPortalSession` (HMAC-SHA256 over a base64url JSON payload of `actor` (`PUPIL` or `GUARDIAN`, task 0040; a cookie signed before it existed has none and is read as `GUARDIAN`, never widened; any other value is not a session), `primaryStudentId`, `allowedStudentIds`, guardian contacts, `issuedAt`, `expiresAt`; constant-time compare, payload rebuilt field by field, 7 days), the cookie helpers (`PORTAL_COOKIE_NAME`, `setPortalCookie`, `clearPortalCookie`, `getPortalSession`), and the sign-in matchers `matchesDateOfBirth` (`YYYY-MM-DD`, `DD/MM/YYYY`, `DD-MM-YYYY`), `matchesPhone` (full number, national digits, or the last 4 or more digits) and `findSiblingStudentIds` (active pupils sharing the guardian phone or email, in any branch). No database row exists, so signing out only clears the cookie. |
| `guard.ts` | `portalGate(req, studentId, capability)`, the one check every portal student route makes: 401 with no session, 400 with no pupil, 403 for a pupil the sign-in does not reach, 403 for another child when the actor's `siblings` setting is off (read NOW, not when the cookie was signed), and 403 `PORTAL_ACCESS` ("Your sign-in does not include this.", one message for every capability) when the pupil's branch does not let this actor do it. Returns the session and the actor's access for the pupil asked about. |
| `secret.ts` | `portalSecret`, `portalSecretProblem`, `PortalSecretError`, `PORTAL_SECRET_ENV`: the cookie signing key, read only from `SESSION_SECRET` (at least 32 characters, at least 10 distinct, not the retired published default; `AUTH_SECRET` is no longer read). No fallback: signing or verifying without a valid secret throws, and `src/instrumentation-node.ts` exits the process at start-up. |
| `service.ts` | `authenticatePortalViaToken` (a `GuardianLinkToken` by SHA-256 hash, unexpired; it stamps `usedAt` but never rejects a used link) and `authenticatePortalViaAdmission` (admission number matched case-insensitively and exactly with raw SQL, active pupils only, at most 5 candidates; secret = date of birth, guardian phone or guardian email; every failure returns `PORTAL_SIGNIN_FAILED`), both returning the signed cookie value with the pupil and siblings, the `actor` (a date of birth is a `PUPIL`; a phone, e-mail or link is a `GUARDIAN`) and the access for each linked pupil. Siblings are looked up only when the branch's setting for that actor allows it. `portalAccessFor(students, actor)`; `getStudentPortalOverview` and `getStudentPortalResults` take `showFees` and, when false, carry no fee figure at all (a blocked report card says only that it is not available yet). Also `resolvePortalSessionData` and the readers `getStudentPortalOverview`, `getStudentPortalResults`, `getStudentPortalInvoices`, `getStudentPortalLms`, plus `submitPortalAssignment`, `attemptPortalQuiz` and `PortalLmsError`; each checks the pupil is in `allowedStudentIds` first. |

## API routes: Parent and student portal (`/api/v1/portal/`)

The portal has its own sign-in and does not use staff sessions or `withAuth`: `session` issues an HMAC-signed cookie (`aleemaan.portal-session`, `__Host-` prefixed over https, 7 days) and every other route reads it with `getPortalSession`, answers 401 without a valid one and 403 when the `[studentId]` in the URL is not in the session's `allowedStudentIds` (the pupil plus siblings sharing a guardian phone or email); only the sign-in is rate limited.

| Method | Route | File | Who | Description |
| --- | --- | --- | --- | --- |
| DELETE, GET, POST | `/api/v1/portal/session` | `portal/session/route.ts` | Anyone (public); GET needs the portal cookie | POST signs in (the answer carries `actor` and `access` per pupil) with `{ token }` (a guardian link token) or `{ admissionNo, secret }` (date of birth, guardian phone or guardian email); input is length-bounded and control or bidirectional characters are refused. CSRF, then 30 per IP and, for the admission-number form, also 5 per IP plus admission number and 10 per admission number per window, all refunded on a correct sign-in; a bad body is 400 and a failed sign-in 401 (every admission-number failure carries the same `PORTAL_SIGNIN_FAILED` text). Sets the cookie and returns `{ student, siblingStudents }`. GET returns `{ session, students }` or 401. DELETE (CSRF-checked) only clears the cookie: nothing is revoked server-side. |
| POST | `/api/v1/portal/students/[studentId]/assignments/[assignmentId]/submission` | `portal/students/[studentId]/assignments/[assignmentId]/submission/route.ts` | Portal session through `portalGate`: a pupil the sign-in reaches, and the actor needs `submitWork` in that pupil's branch | A pupil (or linked guardian) hands in coursework. CSRF and portal cookie; body checked by `submitAssignmentSchema` (text and/or attachments). `submitPortalAssignment` takes the branch and class from the pupil's active enrolment: 404 for an assignment outside it, 400 once the work is `GRADED` or when the deadline passed without `allowLate`; a later hand-in replaces an earlier one. 201 `{ status, submittedAt }`. |
| GET | `/api/v1/portal/students/[studentId]/invoices` | `portal/students/[studentId]/invoices/route.ts` | Portal session through `portalGate`: a pupil the sign-in reaches, and the actor needs `invoices` in that pupil's branch | `{ invoices }`: the pupil's non-cancelled invoices with period and session, every payment on them (any status, newest first) and the discounts. Read-only: no payment can be started from here. |
| GET | `/api/v1/portal/students/[studentId]/lms` | `portal/students/[studentId]/lms/route.ts` | Portal session through `portalGate`: a pupil the sign-in reaches, and the actor needs `materials (the quizzes are left out unless takeQuizzes)` in that pupil's branch | The pupil's published `assignments` (with their own submission and a `closed` flag), `quizzes` (questions without the answer key, plus the last attempt) and `materials`, for the branch and class group of their active enrolment. Empty lists when the pupil has no class. |
| GET | `/api/v1/portal/students/[studentId]/overview` | `portal/students/[studentId]/overview/route.ts` | Portal session through `portalGate`: a pupil the sign-in reaches, and the actor needs `overview (the fee totals only with invoices)` in that pupil's branch | The pupil's record with active enrolment, attendance counts and percentage (late counts as present; 100 when nothing is recorded) with the last 10 records, a fees summary over non-cancelled invoices, and the 5 latest published announcements for their branch or the whole school. 404 for an archived or missing pupil. |
| POST | `/api/v1/portal/students/[studentId]/quizzes/[quizId]/attempt` | `portal/students/[studentId]/quizzes/[quizId]/attempt/route.ts` | Portal session through `portalGate`: a pupil the sign-in reaches, and the actor needs `takeQuizzes` in that pupil's branch | A pupil takes a quiz: `{ answers: [{ questionId, answer }] }`, CSRF and portal cookie. Graded on the server against the answer key; 201 `{ score, isPassed, totalPoints }`. Each call stores a new `QuizAttempt`: no attempt limit, no rate limit, and the quiz time limit is enforced only by the page's countdown. |
| GET | `/api/v1/portal/students/[studentId]/results` | `portal/students/[studentId]/results/route.ts` | Portal session through `portalGate`: a pupil the sign-in reaches, and the actor needs `results (the amount owed only with invoices)` in that pupil's branch | `{ reportCards }`, one per period, from results with status `PUBLISHED` or `LOCKED` (subject lines, remarks, total and average). When the approved global setting `block_unpaid_report_cards` is on and the pupil owes money it returns `reportCards: []`, `blockedByUnpaidFees: true` and the balance instead. |
