## 1. Objective

An administrator can attach a person who already belongs to one branch to others, from the person's row, and can invite someone to several branches in one go. Nobody is attached without accepting: the person opens a link for each branch.

## 2. What already existed (not rebuilt)

A person can already hold one `Membership` per branch (`@@unique([userId, branchId])`). Inviting someone who belongs to one branch to another already worked through the invitation flow (`POST /api/v1/invitations`, the mailed link, `/api/v1/invitations/accept`; `tests/e2e/users.spec.ts`, "someone who already belongs to one branch can be invited to another"). What was missing: the Users page had no "add to another branch" action, and the invite dialog took one branch at a time.

## 3. Decisions

- **D1. Invitation, not instant attach. DECIDED (the coordinator, 2026-11-18: final).** Attaching a person to another branch is BY INVITATION that the person accepts, never a silent attach by an administrator. It is also the secure design, and the one the app already has: the person's own acceptance is the proof (an existing account is attached only by its owner, `acceptInvitation`). Instant attach would let an administrator put a person into a branch against their will and, for a person who is also a parent in one branch and a member of staff in another, widen what they can see without their knowing. Not built, and not to be: the decision is final.
- **D2. An optional `branchIds: string[]` beside the old `branchId`** (`POST /api/v1/invitations`). Exactly one of the two; the old contract (`branchId`, answer `{ invitation }`, a waiting invitation to that branch replaced) is not changed. `branchIds` has 1 to 10 distinct ids (`MAX_INVITATION_BRANCHES`, in the client-safe `rules.ts` so the dialog uses the same number), a duplicate is a 400 (`Choose each branch once.`), and the answer is `{ invitations }` (a list, even for one branch).
- **D3. All or none, and the authority is asked first, for every branch.** `createInvitationsIn` takes the advisory lock on the address (the single invitation's lock), asks `authorityToInvite` of EVERY branch (an unknown branch, a branch the caller does not administer, an `ADMIN` role by a non-superadmin: the single invitation's own rule, extracted into one function that `createInvitationIn` now uses too, so the rule has one home), and only then asks each branch's own conflicts (`membershipRefusal`, the same function again, and a link still waiting). Nothing is written until every question has been answered "yes", so a refusal needs no rollback and a database failure rolls back everything (the route runs it in one transaction). Authority first matters for secrecy: a branch administrator who names a branch that is not theirs gets the single route's 403, with the same words and no branch name, **even when the person is a member there** (a 409 would have told them).
- **D4. A conflict in a branch the caller administers is named.** `That person is already a member of <branch>. Nothing was sent.` (409 `ALREADY_MEMBER`), `That person was deactivated, so they can't be added to <branch>. Reactivate them instead. Nothing was sent.` (409 `DEACTIVATED_MEMBER`), `An invitation to <branch> is already waiting for that address. Revoke it or leave <branch> out. Nothing was sent.` (409 `INVITATION_PENDING`). The details path is `body.branchIds`, so the dialog shows the sentence under the branches.
- **D5. A waiting link is refused, not replaced, when several branches are named** (the maintainer's rule: a pending invitation for ANY branch fails the request). The single route still replaces it, as it always did. An EXPIRED invitation is not waiting: it is revoked and audited and replaced, as in the single route (`writeInvitation`, shared).
- **D6. One e-mail, one link per branch, no migration.** The invitation model is one row and one token hash per (address, branch); a single link that accepts them all would need a new table or a column. Instead `invitationsEmail` names every branch ("as Parent in 3 branches: A, B, C") and puts `For <branch>:` and the branch's own link under it, so the HTML version draws a button under each name (and a branch whose name looks like an address can never become a link, because the line above it is `For ...`). A link works once and adds that branch only. One branch (a `branchIds` list of one) is mailed with the ordinary one-branch text, word for word. `mailInvitations` counts ONE message against the address's mail limit (5 per 5 minutes). A new person who accepts the first link chooses a password; the others need that account to be signed in (the accept page already says so), which is the existing rule for an existing account.
- **D7. Rate limits.** Each invitation counts once against `invite:create:<administrator>` (30 per 5 minutes), so naming ten branches is not a way round it; the per-address limit (3) counts once per request. One audit entry per invitation (`INVITATION_CREATED`, with the branch), none with a secret, plus the `INVITATION_REVOKED` of an expired one it replaces.
- **D8. The dialog keeps the Branch select.** "Invite someone" opens as before (a Branch select, "Send invitation": every existing spec and the walkthrough chapters that use `getByLabel("Branch").selectOption(...)` are untouched). When the caller has more than one branch, a button, "Invite to several branches", swaps the select for a labelled group of checkboxes with "Select all" / "Clear selection" (at least one required; the pick carries across both ways), and the request becomes `branchIds`. The button is a button, not a checkbox, because a checkbox labelled with the word "branch" would also be found by `getByLabel("Branch")` and break those specs. Trivial to make the checkboxes the only way, at the price of rewriting about ten selectors.
- **D9. "Add to another branch" is a row action** (`Add <name> to another branch`, in the `ActionsMenu`, for an active person the caller may touch; drawn only when the caller can invite to more than one branch, since with one there is nowhere to add anyone). It opens the same dialog with `person`: the address is read-only, the role defaults to the one they hold, and only the branches the caller administers less those the person holds or has a link waiting for are ticked-able. The held branches come from the existing `GET /api/v1/members?q=<address>&status=all` (which already shows a branch administrator only their own branches), plus the row's own branch and the open invitations the page already holds; nothing new is exposed. The others are listed as "Not offered: <branch> (already a member)". A person in every branch the caller can offer gets a sentence and a disabled button. If the lookup fails, every other branch is offered and the server names the one it refuses.
- **D10. Messages are toasts.** `UsersPanel` takes `useNotice()` from `components/ui/Toaster` (task 0096, PR `claude/toasts`) in place of its local `useState<Notice>`: the same one-line change that PR makes, so the two merge as one. The success sentences after an invitation (`Invitation sent to ...`, `N invitations created for ...`) therefore appear as a toast; the errors of the dialog's own form (a branch that cannot take the person, a mistake in the address) stay in the dialog, as the toasts task decided. The specs read the sentence through `getByRole("status")`, which finds a toast and the old banner alike.
- **D11. `BranchPicker` is not used.** It is the page-level bar "BRANCH: <name> + Switch branch" (task of `claude/list-grid-views`, used by the Classes and Sessions panels): it says which branch a PAGE is showing. This feature shows no such context: the Users page lists every branch's people, and the invite dialog's Branch field (and its checkboxes) is the TARGET of an invitation, found by `getByLabel("Branch")` in about a dozen specs and the walkthrough; swapping it would rename it "Switch branch" and break them, and it would say the wrong thing (a branch being switched to, not an invitation's destination).
- **D12. `tests/e2e/helpers.ts`**: `ROW_ACTION` learned the label shape `Add <person> to another branch` (the name is in the middle). The only existing spec file changed.

## 4. Not in this task

An instant attach by an administrator (D1); one link that accepts every branch (D6); changing the single `branchId` contract; a "several branches" mode for the bulk import (one branch per file, as before).

## 8. Risks

- The branch list of "Add to another branch" is computed in the browser from the members list (`q` search, at most 64 characters, 100 rows): for an address longer than 64 characters it is not looked up and the server is the check. Harmless: the server refuses the whole request and names the branch.
- A second link of a new person's invitation needs them to sign in first (D6): said by the accept page, but a person may be surprised. The e-mail could say so; left out to keep the text short.
- The "Select all" ceiling is 10 (the API's); a school with more than ten branches would see the rest ticked one by one.
