## 1. Objective
Every route of the Forms module has a screen a person can reach by clicking, so that a teacher can set and mark a practice set, a questionnaire and paper work, a pupil can take them, anyone with the link can answer a public questionnaire, and a reviewer can handle reports on questions. Nothing about who may see what changes: the APIs already decide that (task 0032, slices 3 to 10, and 4l to 4q); the screens only show it.

## 2. Context & Related Docs
- The APIs and their rules: `docs/tasks/0032-forms-and-question-bank.md` (4d to 4q); the design: `docs/development-history/forms-and-question-bank-design.md` sections 8 to 10 (flows and screens).
- Why now: the scan of task 0033's P0 found 54 of 184 routes with no trace of a screen; about 35 are the Forms module and the pupil's practice, 6 are question-bank reports, printing and offer-back. The maintainer chose to build the screens and then walk the product, not to walk first (D1).
- Conventions to follow: a server `page.tsx` (session, `PageHeader`, display-only role checks), a client sections component with the ARIA tabs pattern (see `QuestionBankSections.tsx`), panels that call the API with `getJson`/`sendJson` (`components/auth/postJson.ts`), `Dialog`, `TextField`, `SelectField`, `Alert`, theme tokens only, both themes, phone width, axe clean.

## 3. Rules every screen keeps (the maintainer's, made explicit)
1. **The answer key and the explanation are shown only where the API returns them** (a manager of the form, or a pupil after the rules let them see it). A screen never fetches a key to hide it.
2. **An anonymous questionnaire shows no respondent**, not even in a count small enough to point at someone: the summaries show what the API returns, with its small-count hiding, and say so.
3. **Display only**: hiding a button is a courtesy, the API refuses. Every screen has a refusal sentence for when the API says 403/404 (never a status code, never an empty page).
4. **No pasted markup**: question and answer text is rendered as text.
5. **A pupil's time limit is shown and counted down**; the server decides (60 s allowance); a refused submit says what happened and keeps the pupil's answers on screen.
6. **Absent is not zero**: a result that does not exist yet is not shown as 0.

### Slice F1: Staff forms: list, create, publish, close (`/forms`, nav "Forms" for administrators and teachers)

- [x] The builder per kind in one dialog: practice set (title, instructions, class groups, window, time limit, questions written here: single choice, multiple choice, true/false, short answer, each with its correct answer, points and explanation), questionnaire (members or anyone with the link, anonymous or not, roles, window, questions of the kinds the API allows: single, multiple, short, long text, rating), paper work (title, at least one class, window, time limit). Adding a question from the question bank (which copies it) is not in F1; it follows with the form's page.

- Known limit: non-teaching staff have no navigation entry for Forms (the entry is for administrators and teachers), so their "For you" section is reached by the address `/forms`. Whether the entry should show for them is a decision for the maintainer.
### Slice F2a: A form's page (`/forms/[id]`): overview, questions, results
- [x] The page: `/forms/[id]` (a server page that finds the form's branch and kind and shows a sentence for an unknown form or one in a branch the person is not staff in; every list row's title links to it), a back link to Forms, the title and status, tabs by kind: Overview, Questions, Results (a paper-work form has Overview only until F2b)
- [x] Overview: the details (status, window, time limit, classes, who answers, anonymous, who wrote it, how many answered), Edit details (title, instructions, window, time limit, classes), Publish, Close with a confirmation, the public link of a public questionnaire (the same copy button and the same words as the list), Print (a dialog: include the answer key for whoever manages the form, an optional reason, "Download PDF"). A refusal is shown as a sentence that says who may change a form.
- [x] Questions: numbered, with the kind, the options, the points, the explanation and which questions are marked by hand; the correct answers appear only where the API sends them (whoever manages the form), and a sentence says so otherwise
- [x] Results: a practice set's responses (pupil, admission number, finished or in progress, the score as "x of y"; no score yet is shown as a dash, never 0); a questionnaire's summary (how many answered, each choice question as counts and percentages, written answers listed without names), and when an anonymous questionnaire has too few answers the sentence that the breakdown appears once enough people have answered, with the count so far

### Slice F2b: Marking and the paper-work roll call
- [x] Marking: a "Marking" section on `/forms` (the queue across the branch's forms, with a filter: waiting or partly marked, waiting, partly marked, marked) and a "Marking" tab on a practice set's page when it has a question marked by hand (that form's queue). One response at a time in a dialog: the pupil's answers by kind, automatically marked ones read-only with their score, hand-marked ones with a score (from 0 to the question's points) and feedback; the model answer for whoever manages the form; "Save marks" sends the answers given a score (a partly marked attempt is allowed); the history of who marked what. A score outside 0 to the points is refused on the screen with a sentence and nothing is sent.
- [x] The builder: a practice set's short-answer question gets "Marked by hand" (ticked: the API's default; unticked: marked automatically against the accepted answer)
- [x] Paper work roll call: a "Roll call" tab on a paper-work form's page: the summary (handed in, late, still to hand in, asked for marking), the roster with a status and a note per pupil, "Save changes" for the batch of changes made, "Add pupils who joined the class" (sync), the pupils who asked for marking flagged. A paper handed in after the closing time is recorded as late (the API's rule, said on the screen).
### Slice F3: The portal: forms (a "Forms" tab in `/portal`, for the pupil)
- [x] The tab: shown to a pupil who may open the overview, never to a guardian (every portal forms route answers a guardian 403, so the screen does not offer what the API refuses); sections Practice sets, Questionnaires, Paper work
- [x] Practice sets open for the pupil's class: the list (questions, time limit, closing time, "Start", "Continue" for an attempt in progress, the score of a finished one), the attempt on its own screen with the questions by kind and a countdown from the time the attempt started (the server decides: it allows 60 seconds more; a refused submit says what happened and keeps the pupil's answers on screen), "Submit", the result with what the rules reveal: an answer the machine marked shows whether it was right, the correct answer and the explanation; an answer waiting for the teacher says so, shows no score and no key, and the total is "so far", never a final-looking zero; a finished attempt can be opened again from the list; "Download PDF" of the result
- [x] Questionnaires addressed to the pupil: the list with "Answered", answered once in a dialog, the anonymity sentence before answering (the question fields are shared with the staff "For you" dialog, so they are one component)
- [x] Paper work: the list with the pupil's own state (not handed in, handed in, handed in late, asked for marking), the closing time, "Request marking" while the API allows it and its own sentence when it does not
- Not in F3: letting a pupil start a finished set again (the API would allow a new attempt; whether it should is a question for the maintainer, noted in the PR)
### Slice F4: The portal: question practice (a "Practice" tab)
- [ ] The tab: a "Practice" tab in `/portal` for whoever has the overview and a practice level other than NONE (the session already returns each student's access with the guardian's level held to the school's ceiling). A pupil at FULL has three sections: Practise, History, My reports. Anyone at SUMMARY (a guardian by default) has one view, how practice is going (sessions, questions, accuracy, by subject and topic), and never a question. A guardian at FULL (an administrator's choice) sees the history only, read only: starting, answering, finishing, archiving, reporting and printing all refuse a guardian, so the screen does not offer them.
- [ ] Practise: the setup (subject, topic, size from the school's presets, feedback "After each answer" or "At the end", how many questions are left today of the daily cap; a closed practice, a spent cap and a pool too small each say so in the API's own sentence and nothing can be started), then the session one question at a time with progress ("Question 2 of 10"), the answer fields shared with the Forms screens, "Check answer" (after each answer: right or not quite, the correct answer and the explanation, as the API reveals them) or "Save answer" (at the end: nothing revealed), "Finish now" with a confirmation (the questions not answered are given back to today's allowance), and at the end the summary of the session (x of y right, the accuracy, every answer with the key and the explanation). A refused answer keeps the pupil on the same question with the sentence and the answer still in the field.
- [ ] History: the pupil's sessions, newest first, each with subject, topic, date and "x of y right"; a finished session opens to its answers (the question, your answer, right or not, the correct answer, the explanation); "Archive" and "Restore" on an answer with a "Show archived answers" switch; "Download PDF" of a finished session (the API prints finished sessions only); a session left open (the page was closed mid-way: nothing in the API reopens a session) shows "Not finished", how many were answered, and "Finish it", which gives the unanswered questions back; its answers are not listed until it is finished, so a session set to show answers at the end keeps that promise.
- [ ] A report on a question just practised: "Report a problem" on an answer in the summary and in the history opens a dialog (at least 5 characters, said on the screen and nothing sent below that), the API's refusals (already reported, reporting switched off, limits) are shown as the sentence it sends; "My reports" lists what the pupil reported with its state (waiting, resolved, dismissed) and, when a reviewer has answered, the outcome and the reason the reviewer gave.
- [ ] One additive API change: `finish` and `history` named each answer by the option's id only ("B"), because they left out the kind and the options of the question, so a history could not say "Mitochondria". They now carry `type` and `options` (both already shown to the pupil when the question was asked; never the key). Failing-first API assertions in `tests/api/pupil-practice.spec.ts`.
- Not in F4: reopening a session after a reload (no route for it: the questions of a started session are not sent again), skipping a question, a retake of a single question. Found while reading the service, for the maintainer: a pupil who closes the page mid-session leaves it open, and its unanswered questions count against the daily cap until it is finished (the History's "Finish it" is the way back).
