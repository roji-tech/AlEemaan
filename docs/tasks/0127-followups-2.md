# 0127: template versions, Complete for an unplaced draft, Department in the invitation file, the remembered branch per person

- **Status:** In Progress: built; tests running. One migration, `20261122130000_template_snapshot_invitation_department`.

The maintainer (2026-11-21): "proceed" on the four items left in task 0126's "not done": template versions (editing a template in place changes earlier terms), Complete for an unplaced draft, the Department column of the pupil and invitation files, and the remembered branch (per browser, not per person).

## Decisions
1. **Template versions, as a snapshot.** `ResultTemplateUse.snapshot` (JSON, nullable): the look (`layout`: code, name, options as the card resolves them) and the live trait groups with their live traits, taken by the FIRST publish of a class's results for a term (the same transition that records the template; later publishes leave it). The card's look (`layoutForClass(…, periodId)`) and its trait groups (`traitView`) read the snapshot when there is one. Editing the template afterwards (its look, a trait renamed, archived or added, a new group) changes terms published after the edit, never the ones before it; an unlock that leaves nothing of the class published clears the record, so the next publish takes a fresh snapshot. Ratings are by trait id, so a trait renamed or archived later still shows its rating under its old name in the old term. A record with no snapshot (made before this, or damaged) follows the live template as before. Marks never depended on this: schemes and grade scales are already versioned and locked by the first result. Not versioned: the template's name shown on the trait sheet, and the school-wide template master (a branch follows it by copying into its own template row, which is what the snapshot freezes).
2. **Complete for an unplaced draft.** `POST /api/v1/staff/unplaced/[id]/complete` (a superadmin only; a branch administrator and a placed record get the same 404 as an unknown id), the same check as any record (names, kind, gender, and an e-mail or a phone; 409 `INCOMPLETE` listing what is missing). The staff screen's Complete button and the "Complete" and "Mark as draft" menu items work under "Not placed in a branch" through the unplaced routes.
3. **Department in the invitation file.** An optional "Department" column, staff roles only: matched by name (any capitals) to a live department of the branch; a problem on the row for an unknown department, or for a student or a parent; ignored, with a note, while the branch does not use departments. `Invitation.departmentId` carries it (draft or sent); accepting puts the person in the department as a member, never its head, when the branch still uses departments, the department is still live and the person has a staff record (a staff role always gets one). **The pupil file gets no Department column:** departments group staff and subjects; a pupil is in a class, so the column would mean nothing.
4. **The remembered branch per person.** `User.lastBranchId`, written by `PUT /api/v1/account/branch` (the person's own; only a branch they belong to, or any for a superadmin; else 404) when they choose a branch on a page with a picker, and read by the app layout into `BranchMemoryProvider`, so the first paint already has it and it follows the person to another browser or device. It replaces the browser's localStorage memory (which another person on the same browser inherited). A page still uses it only when it is one of the branches the person may see (`pickBranch`). The request uses `keepalive`, so leaving the page straight after choosing does not lose it.

## Not done
A "versions" screen to look at or restore an earlier look of a template (the snapshot is kept, not shown); a Department column in the pupil file (no meaning, see 3).
