# 0126: the follow-ups: card download options, subject order, template record, department review, unplaced staff in bulk

- **Status:** In Progress: built; tests running. One migration, `20261122120000_subject_order_template_use`.

The maintainer (2026-11-21): "quickly complete these now": a manual per-class subject order; recording which template a published report card used; the downloadable HTML card ignoring the new show/hide options; and the older follow-ups of tasks 0101 and 0118 (the Department review browser test, the Review tab's waiting-groups view, bulk import and export of unplaced staff, heads' "Add to department").

## Decisions
1. **Downloadable card.** `generateReportCardHtml` reads the same layout options as the screen: the class arm and the "Public Verification Records" block are printed only when the option is exactly `true`; silence hides them (task 0121). The signature boxes are unchanged (the download always had them).
2. **Subject order.** `SubjectOffering.sortOrder` (nullable). The order of `subjectIds` in the existing save (`PUT /academics/class-groups/{id}/subjects`) IS the order: no new route. The class list returns them in that order. The report card puts subjects with a place first, in that order, then the rest in the order they were added (`orderBySubjectAdded(rows, added, position)`). The Subjects dialog of a class gets "Order on the report card" with Up and Down per subject. A class nobody ordered by hand prints exactly as before.
3. **Template record.** `ResultTemplateUse` (branch, period, class, template; unique per branch, period and class), written by the transition that publishes a class's results for a term (the first publish; later ones do not overwrite) and cleared by an unlock that leaves nothing of the class published for the term. `templateForClass(branchId, classGroupId, periodId?)` answers the recorded template when there is one, else the class's current one; the card's look and its trait groups use it. Moving a class to another template afterwards no longer changes how a published term prints. NOT covered: editing the template itself in place (its look, its traits) still shows in every term that used it; that needs template versions. A deleted template takes its records and the term follows the class again.
4. **Department review.** A browser spec for the tab (the head sees the waiting groups, passes one, returns another with a reason). The Review tab's queue now carries `awaitingDepartment` per group (submitted results of a department's subject with no review, only while the branch asks for reviews); the group shows "N waiting for the department review" and its Approve button is disabled (the server refuses it anyway).
5. **Unplaced staff in bulk.** `POST /api/v1/staff/unplaced/import` (a superadmin only; no branch in the body; all or none; a live unplaced record's address is a problem on its row; no department column; never a sign-in) and `POST /api/v1/staff/unplaced/export` (a superadmin only; rows chosen on the server; audited as `EXPORT_CREATED` without the data; rate limited with the other exports). The "Not placed in a branch" view of Academics > Staff gets "Add many" and "Export".
6. **Heads' "Add to department".** The staff list's tick boxes and selection bar are shown to a head of department (not an administrator of the branch) too: they may tick people (not drafts or archived) and "Add to department" offers only the departments they head; the invitation buttons stay an administrator's. The department list is loaded for every viewer of a real branch; it marks which departments the person may manage, so anyone else is offered nothing.

## Not done
Template versions (so editing a template in place no longer changes earlier terms); a Complete for an unplaced draft before it is placed; the bulk invitation and pupil files' Department column; the remembered branch per user.
