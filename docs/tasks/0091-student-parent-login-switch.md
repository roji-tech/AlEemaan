# 0091: Student and parent sign-in switches, per branch (off by default)

- **Period / Focus:** 2026-11-18 (the maintainer: "we want superadmin/admin to be able to turn on/off student and parent login, it will be off by default"; then, after the first design was school-wide: "admin can only switch on login for the student/parent in his branch or branches; superadmin can switch it for all or some branches")

- **Priority:** High (it decides who can reach the school's data from outside, and it LOCKS OUT every existing student and parent account until a switch is turned on)

## 1. Objective

Every branch has two switches, **student sign-in** and **parent sign-in**, both **off by default**. A person whose only active roles are STUDENT and/or PARENT cannot sign in, and a session they hold stops working, unless at least one of their memberships is in a branch whose switch for THAT role is on. An administrator turns the switches on and off for the branches they administer; a superadmin for any, several or all.

## 2. Decisions

- **D1. Per branch, not school-wide.** The first build was one pair of switches on `SystemSettings`; the maintainer's second message made it per branch, and that build is gone. Two `Boolean` columns on `Branch` (`studentLoginEnabled`, `parentLoginEnabled`, `@default(false)`), migration `20261118160000_student_parent_login_switch` (`ALTER TABLE public."Branch" ADD COLUMN ... boolean NOT NULL DEFAULT false`, additive, a constant default, safe on a live table). Columns on the branch, not a small table: the rule reads them through the membership's branch in a join the session lookup already does, and there are two values per branch and no history to keep (the history is the audit log).
- **D2. The rule** (`lib/auth/login-switch-rules.ts`, pure). A STUDENT membership needs the student switch of its own branch; a PARENT membership the parent switch of its own branch; a membership in a closed branch does not count. A person is closed only when every active membership is student or parent and none is open. **Never affected:** anyone with any other active role (administrator, teaching or non-teaching staff), a parent who is also staff, and any superadmin. A person attached to several branches works in the branches that are open and only those (the pages and API already limit them to the branches they belong to). A deactivated membership is no membership.
- **D3. Who may change what.** `roles: [ADMIN]` admits a superadmin and an administrator; everyone else (teacher, staff, student, parent) is 403, signed out is 401. What each may touch is decided by `adminScope`: a superadmin every branch, an administrator only the branches where they hold an ACTIVE `ADMIN` membership. The body is `{ branchIds: string[] }` (1 to 200 unique ids) **or** `{ allBranches: true }` (exactly one), and `studentLoginEnabled` and/or `parentLoginEnabled` (real booleans), nothing else (strict). For an administrator every id must be one of their branches, otherwise **the whole request is refused with 403 and nothing is changed**; a branch that does not exist gets the same answer, so the answer never says whether another branch exists. For a superadmin an unknown id is a 404 and nothing is changed. **`allBranches` for an administrator means "all of MY branches"** (never another); for a superadmin it is every branch. (An administrator's `allBranches` was an open choice; "all of mine" keeps one rule: the caller's reach is the list.)
- **D4. All or nothing, audited.** All the named branches are changed in ONE transaction. Their rows are locked `FOR UPDATE` in id order (two overlapping changes cannot deadlock, and each audit entry shows the true before). One `AuditLog` entry `LOGIN_SWITCHES_CHANGED` per branch that changed (target type `Branch`, the branch id, before and after, each with the branch name), written in the same transaction. A branch already as asked writes nothing. A branch deleted between the read and the lock refuses the whole request.
- **D5. The sign-in refusal, and what it says.** Before the password is proved every failure is the one generic `401 INVALID_CREDENTIALS` (no account-existence leak; the sign-in portals' wrong-portal refusal is unchanged). **Once the credentials are right** and none of the person's branches is open, they get `403 LOGIN_CLOSED` with "Sign-in for your school is closed at the moment. Please try again later or contact your school administrator.", no cookie, no session and no two-step challenge. The maintainer asked for this: the person holds the password, so it tells nobody anything they do not know, and a pupil is not told "invalid password" for a school that has simply not opened yet. It is **not counted as a failed attempt** (the reservations are refunded: the credentials were right). `completeSignIn`, the one place a session is made, asks again (so a two-step code entered after the branch was closed is refused too, with the same message).
- **D6. Existing sessions.** The session lookup reads the person's active memberships with their branches' two switches in the SAME join as the session (a nested join of a few small rows), and `loginClosedFor` decides in memory. So a closed branch ends its students' and parents' sessions **on their very next request, on every server**, with no extra query and **no cache** to go stale (the first build had a five-second per-process memory; reading the switches with the session made it unnecessary). The lookup answers `"closed"`: an API call gets `401 LOGIN_CLOSED` with the message above (not the generic "Authentication required"), a page redirects to `/login?closed=1`, whose notice is fixed text whatever the address says. The session row is **not deleted**: opening the branch again resumes it. Staff never pay anything: the check is pure on what was just read.
- **D7. No back door.** A session is made in one place (`completeSignIn`). A password reset, an accepted invitation and an e-mail confirmation sign nobody in (they never did), and a new password does not open a closed door. A magic link does not exist for accounts. The public result portal (`/portal`, admission number or guardian link) is **not** touched: it is a separate door with its own rules.
- **D8. The public sign-in page.** The page cannot know the branch before sign-in, so on the student. and parent. hosts it shows "Student/Parent sign-in is closed at the moment..." **only when NO branch at all** has that portal's switch on, decided from the host alone (never from anything typed). Otherwise the normal form. The administrator and staff portals never show it.
- **D9. The screen.** `LoginSwitchPanel`: a list of the branches the person may switch, each with two labelled checkboxes ("Students can sign in", "Parents can sign in"; unchecked = off), applied when pressed (one request for one branch), result in a polite live region ("Student sign-in is now off in Primary (English). Students who are signed in there are signed out on their next click."), a refusal as an alert with "Nothing was changed". A superadmin also gets a checkbox per branch, "Select all", "Clear" and four bulk buttons for the selection (one request, all or nothing). It is the **Sign-in access** tab of Settings (a superadmin) and the top of the **Users** page for an administrator who is not a superadmin (they cannot open Settings; they see only their own branches, one row when they have one). The shared Toaster (`useNotice`) and `BranchPicker` are NOT on `dev` yet (they are on branch `claude/toasts`), so importing them would break the build: the existing always-present live region with an `Alert` is used for the result message, and swapping it for `useNotice` is a small change in `LoginSwitchPanel.tsx` once the toasts merge. The panel lists every branch itself, so it needs no branch picker. The shared list/grid kit was not used (not merged).
- **D10. Tests keep working.** The test database has the switches ON for every branch that exists (`seedInstance`, which `createUser` calls, opens them), except in a spec that says `manageLoginSwitches(true)` (this task's own two). No existing spec was edited.

## 3. Rollout, and the migration order

The production workflow runs from the `prod` ref, so the order is: **merge to `prod`, THEN run the migrate-production workflow** (the maintainer's). Until the migration has run, the new code cannot read the two columns, and **every sign-in and every request of a signed-in person fails** (the session lookup selects them): run it straight after the deploy, with no gap. Once both have happened, **no student or parent can sign in, and a signed-in one is signed out on the next request, until an administrator of their branch (or a superadmin) turns the switch on** in Settings (Sign-in access) or on the Users page. Say so to the school before the release.
