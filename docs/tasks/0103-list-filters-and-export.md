## 1. What exists (read from the screens and the code)

- **Pupils:** the Filters panel has one control, Show (current, suspended, expelled, archived), plus the search box (name or admission number). The list is **paged by the server** (25 to a page in the list, 24 in the grid, the page size is sent as the limit), so a filter has to be applied by the server or the counts and pages lie.
- **Staff:** Show (current staff, archived) and the search box; the whole list is loaded and filtered in the browser. Each row already knows its kind (Teaching or Non-teaching).
- **Classes and subjects:** a "gap" filter (no subjects set, no arms; unused subjects). Their lists are loaded whole.
- **Export:** none. The bulk import has Excel and CSV **templates**, so the columns of each list are already defined (`pupilEntity`, `classEntity`, `subjectEntity`, `staffEntity`).

## 2. Design

- **D1. Pupil filters: Class, Gender, Age**, in the same Filters panel as Show. Class is one of the branch's classes, or "No class yet" (a second control narrows to an arm once a class is chosen). Gender is Male or Female. Age is "from" and "to" in whole years, **as of today** (the school's time zone, `SCHOOL_TIME_ZONE`): a pupil born 12 Mar 2018 is 8 on 18 Nov 2026. Turned into a range of dates of birth by one pure function (`birthDateRange(min, max, today)`, tested at birthdays, leap days and the year boundary). A pupil with **no date of birth is left out** when an age is asked for, and the list says how many were ("14 have no date of birth, so age cannot be checked"). All of it is applied by `GET /api/v1/students` (new query parameters `classGroupId`, `classArmId` (or `noClass=1`), `gender`, `ageMin`, `ageMax`; every value validated; an id from another branch is a 404, never a leak). The Filters button's badge counts what is on; Clear filters clears them all; at 360 px the panel is a stack.
- **D2. Staff filter: Kind** (Teaching, Non-teaching) in the staff Filters panel, applied in the browser as Show is. Room for the filters of task 0101 later (account, department, corps member).
- **D3. Export, one way for four lists.** An **Export** button in the toolbar of Pupils, Staff, Classes and Subjects opens a small dialog: *What* ("The 38 shown now, with the search and filters on" / "Everything in <branch>"; "everything" is the current records, with a checkbox to include the archived) and *Format* (CSV or Excel). The file holds **every row that matches, not only the page on screen**. The **columns are exactly the import template's**, in the same order and wording, so an export can be corrected in a spreadsheet and imported again, and the school's own habits hold. Generated by the server: `GET /api/v1/{students,staff,academics/class-groups,academics/subjects}/export?branchId=&format=csv|xlsx&...the list's own filters` (the same validation as the list, so "shown" can never differ from what the list would return). File name `pupils-primary-english-2026-11-18.csv`.
- **D4. Security of an export** (it is personal data in bulk, leaving the system): only an **administrator of that branch or a superadmin** (a teacher may read the lists but not export them; *ask: do you want teachers to export their own classes?*); the branch comes from the person's authority, never from the request alone; every export is **audited** (who, which list, which branch, the filters, how many rows; never the data) as `EXPORT_CREATED`; limited to 5 exports per person per 5 minutes (the rate limiter of task 0102); at most 20,000 rows, said plainly beyond that; a cell that starts with `=`, `+`, `-`, `@`, a tab or a carriage return is written with a leading apostrophe so a spreadsheet never runs it as a formula (CSV and Excel injection); CSV has a UTF-8 byte-order mark so Excel reads Arabic names; `Cache-Control: no-store`, `Content-Disposition: attachment`. *(ask: should "everything" ever include the archived by default? Proposed: no, a checkbox.)*
- **D5. Classes and subjects export** use the import's own layout: a class is one row with its arms and its subjects in one cell each ("A, B, C"); a subject is one row. They are small lists loaded whole, so "shown" is what the screen shows after its filters and search, written by the browser from the same rows (no server round trip), still through the same cell-safety function; the server route exists too, for the audited, full export.

## 3. Not in this task

Exporting invoices, results or attendance (each has its own rules about who may see it); scheduled or e-mailed exports; the age "on a given date" for admissions cut-offs (*ask: do you need it? "As of today" is what this builds*).

## 4. Tests (to write with the code)

Unit: `birthDateRange` (birthdays, 29 Feb, year boundary, min > max refused), the cell-safety function (every leading character), the export column lists equal the import columns, row builders. API: each filter alone and combined; counts and pages follow the filter; a class of another branch is 404; an export has the same rows as the list for the same filters, all pages, not one; a teacher is refused; another branch's administrator is refused; the audit row has no data; the rate limit; the row cap; the file's headers. Browser: filters at 360, 850 and 1280 px, the badge count, Clear, the export dialog's two choices, a downloaded CSV's first line.
